# TZ-004: Вкладка «Здоровье» (люди, анализы, назначения, задача на приём)

- Статус: done
- Дата: 2026-10-19
- Реализовано: DB v14, вкладка «Здоровье», CRUD людей/анализов/назначений, задача в общем списке
- Требования: [F-009](../features/F-009-health.md)
- Платформа: Android (minSdk как в проекте), Jetpack Compose, локальное хранение
- Оценка: L
- Решения стейкхолдера: макс. **3** человека; назначения = **лекарства + визиты**; задача из назначения видна в общем списке задач

## 1. Цель

Дать пользователю отдельный локальный контур учёта здоровья: до 3 людей → анализы и назначения (лекарства / визиты), с созданием обычной задачи в общем списке дел — без облака и без медицинской интерпретации данных.

## 2. Scope

### In

- Вкладка **«Здоровье»** в bottom bar **между «Заметки» и «Покупки»**
- CRUD **человека** (минимум: имя), лимит **≤ 3**
- Два списка в контексте выбранного человека: **Анализы**, **Назначения**
- Назначения с типом **`MEDICATION` | `VISIT`**
- CRUD анализа и назначения (поля — §5)
- Действие у любого назначения: **«Создать задачу»** → обычная `TaskKind.TASK` в `TaskRepository`, видимая на вкладке «Задачи» (список и календарь)
- Empty / content состояния; подтверждение удаления человека; блок добавления 4-го человека
- Данные только локально; русский UI
- Unit-тесты: лимит 3; дата = today + N; title по типу; задача появляется в observeTasks

### Out

- Медицинские советы, диагнозы, справочник лекарств
- Файлы/фото результатов
- Отдельный push-движок (только через задачи; F-001 отдельно)
- Голос, виджет, шаринг, sync
- Дневник давления/веса/симптомов
- Изменение существующих вкладок Задачи/Заметки/Покупки, кроме вставки пункта навигации

## 3. Сценарии

### Happy path — первый заход

1. Пользователь открывает «Здоровье».
2. Empty-state: «Добавьте человека, для которого будете вести анализы и назначения» + кнопка «Добавить человека» (подсказка: до 3 человек).
3. Вводит имя «Марина» → сохранение → человек выбран → видны пустые секции «Анализы» и «Назначения» с CTA добавить.

### Happy path — лимит людей

1. Уже есть 3 человека.
2. «Добавить человека» недоступно (disabled) и/или snackbar/текст: «Можно добавить не больше 3 человек».
3. После удаления одного снова можно добавить.

### Happy path — анализ

1. Выбран человек → «Добавить анализ».
2. Название «ОАК», плановая дата (опционально), статус по умолчанию «Запланирован».
3. Сохранение → пункт в списке анализов.
4. Пользователь отмечает «Сдан» (и опционально дату сдачи) → статус обновлён.

### Happy path — лекарство + задача «через N дней»

1. «Добавить назначение» → тип **Лекарство**, название «Амоксициллин», дозировка «500 мг», комментарий «после еды».
2. «Создать задачу».
3. Пользователь указывает: через **3** дня, время 09:00 (опционально).
4. Подтверждение → в модуле задач:
   - `kind = TASK`
   - `title` = `"Приём: Амоксициллин"` (или title назначения)
   - `dueDateEpochDay` = сегодня + 3
   - `dueTimeMinutes` при указании времени
5. Вкладка «Задачи» → список/календарь: задача видна в этот день наравне с остальными.

### Happy path — визит + задача на дату

1. «Добавить назначение» → тип **Визит**, название «Терапевт», комментарий «клиника на Ленина».
2. «Создать задачу» → дата визита (или «через N дней»), время опционально.
3. Создаётся `TASK` с title вида `"Визит: Терапевт"`.
4. Задача видна в общем списке задач и календаре.

### Happy path — лекарство + регулярный приём

1. Из лекарства: «Создать задачу» → повтор **ежедневно** (или «свои дни»).
2. Recurring task по правилам `RecurrenceType` приложения.
3. Поведение чекбокса/rollover — как у обычных повторяющихся задач; задача видна в списке.

### Альтернативы / ошибки

| Ситуация | Поведение |
|----------|-----------|
| Пустое имя человека / анализа / назначения | Сохранение запрещено; ошибка у поля |
| Не выбран тип назначения | Сохранение запрещено; тип обязателен |
| Уже 3 человека, попытка добавить | UI блокирует; в репозитории — отказ (идемпотентная защита) |
| Удаление человека | Диалог: «Удалить человека и все его анализы и назначения? Задачи в списке дел останутся.» |
| N ≤ 0 в «через N дней» | Не принимать; минимум 1 |
| Ошибка БД при создании задачи | Snackbar; назначение не портить |
| Нет выбранного человека | Нельзя добавить анализ/назначение |

### Edge cases

- Один человек: переключатель людей можно скрыть, показать имя в шапке.
- Много анализов: сортировка — сначала не сданные по дате (null в конце), затем сданные (Should: зафиксировать в UI).
- Назначение без даты курса — допустимо.
- Повторное «создать задачу» с того же назначения — разрешено (несколько задач).
- Удаление назначения не удаляет уже созданные задачи.

## 4. UI / навигация

| Экран / состояние | Описание | Переходы |
|-------------------|----------|----------|
| Bottom bar | Иконка здоровья (например Favorite/LocalHospital/Medication) + подпись «Здоровье»; позиция: после «Заметки», до «Покупки» | Тап → экран здоровья |
| Health empty (нет людей) | Текст + CTA добавить человека; намёк «до 3» | → sheet человека |
| Health content | Шапка: выбор человека (до 3). Секции: Анализы / Назначения (в списке назначений бейдж типа Лекарство/Визит) | FAB / «+»; «+ человек» скрыт или disabled при count==3 |
| Person editor | Имя*; заметка опц. | Сохранить / Отмена |
| Analysis editor | Название*; статус; плановая дата; дата сдачи; комментарий | Сохранить / Удалить |
| Prescription editor | Тип* (Лекарство \| Визит); название*; для лекарства — дозировка; комментарий; даты курса/визита (опц.) | Сохранить / Удалить / **«Создать задачу»** |
| Create task sheet | Через N дней и/или дата и/или повтор; время опц.; превью | Создать → `TaskRepository`; задача сразу в общем списке |

**Не делать:** отдельный bottom bar внутри здоровья из 4+ пунктов; карточки-дашборды со статистикой в v1.

## 5. Данные и правила

### Сущности (логическая модель)

| Сущность | Поля | Ограничения |
|----------|------|-------------|
| HealthPerson | id, name, note?, createdAt, updatedAt | name не пустой; max 100 символов; **всего ≤ 3** записей |
| HealthAnalysis | id, personId, title, status (`PLANNED` \| `DONE`), plannedDateEpochDay?, doneDateEpochDay?, comment?, createdAt, updatedAt | title не пустой; personId обязателен; при DONE — doneDate = today, если не задана |
| HealthPrescription | id, personId, **type** (`MEDICATION` \| `VISIT`), title, dosage? (для MEDICATION), comment?, startDateEpochDay?, endDateEpochDay?, visitDateEpochDay? (для VISIT, опц.), archived (bool, default false), createdAt, updatedAt | title не пустой; type обязателен; personId обязателен |
| Связь | `health_prescription_task_link(prescriptionId, taskId)` | Задача — обычная `tasks` row, `kind = TASK` |

**Рекомендация:** таблица связей без нового `TaskKind` — задача полностью участвует в списке/календаре/фильтрах.

### Валидации и бизнес-правила

1. `count(HealthPerson) ≤ 3` на уровне UI и репозитория.
2. Каскад: Person → Analyses + Prescriptions (+ links); **Tasks не удалять**.
3. «Через N дней»: `dueDate = todayEpochDay + N`, `N ≥ 1`.
4. Title задачи по умолчанию:
   - MEDICATION → `"Приём: " + title`
   - VISIT → `"Визит: " + title`
5. Notes задачи (опц.): `"Здоровье: " + person.name`.
6. Анализ: статусы только PLANNED / DONE; «просрочен» = UI-состояние (PLANNED и plannedDate < today).
7. Архив назначения: `archived = true` скрывает из основного списка (экран архива — Could).
8. Созданная задача **обязана** появляться в `observeTasks` / UI списка задач без дополнительных фильтров по источнику.

## 7. NFR

- Офлайн-first (N-001), без аккаунта (N-002), русский UI (N-005).
- Не ухудшать запуск: вкладка лениво не требует сети.
- Дисклеймер (один раз или в empty-state мелким текстом): «Не является медицинской рекомендацией. Данные хранятся только на устройстве.»
- Приватность: не логировать содержимое анализов/назначений в crash-reporter plain text (если появится аналитика — маскировать).

## 8. Критерии приёмки (DoD)

- [ ] Порядок вкладок: Задачи → Заметки → Здоровье → Покупки
- [ ] Можно добавить 1–3 человека; 4-й добавить нельзя
- [ ] Переключение людей; удаление с подтверждением
- [ ] CRUD анализов в контексте человека
- [ ] Назначения с типом Лекарство / Визит; CRUD
- [ ] Из лекарства и из визита создаётся задача «через N дней» / на дату / с повтором
- [ ] Созданная задача видна в **списке задач** и календаре как обычная TASK
- [ ] Удаление назначения/человека не удаляет задачи
- [ ] Empty-states понятны
- [ ] Unit-тесты: лимит 3, dueDate, title по типу
- [ ] Нет регрессии Задачи/Заметки/Покупки
- [ ] Edge cases §3
