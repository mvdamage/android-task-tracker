# F-009: Ведение состояния здоровья

- Статус: approved
- Приоритет: Should
- Эпик: Домашний органайзер / здоровье
- Связанное ТЗ: [TZ-004](../tz/TZ-004-health.md)
- Обновлено: 2026-10-19 (решения стейкхолдера: лимит 3 человека; назначения = лекарства + визиты)

## User stories

| ID | Story | MoSCoW |
|----|-------|--------|
| US-H-01 | Как домашний органайзер (P2), я хочу вкладку «Здоровье» между «Заметки» и «Покупки», чтобы вести медданные отдельно от дел и покупок | Must |
| US-H-02 | Как пользователь, я хочу завести до **трёх** человек (себя / членов семьи), чтобы разделять анализы и назначения по людям | Must |
| US-H-03 | Как пользователь, я хочу вести список анализов по человеку (что сдавать / сдано, дата), чтобы не держать это в голове и в заметках | Must |
| US-H-04 | Как пользователь, я хочу вести назначения двух типов — **лекарства** и **визиты** — по человеку, чтобы видеть план лечения и приёмы у врача | Must |
| US-H-05 | Как пользователь, я хочу из лекарства или визита создать задачу (срок / повтор), чтобы она отображалась в общем **списке задач** и календаре как обычная задача | Must |
| US-H-06 | Как пользователь, я хочу отметить анализ сданным / назначение выполненным или архивировать, чтобы список оставался актуальным | Should |
| US-H-07 | Как privacy-conscious (P3), я хочу, чтобы данные здоровья хранились только локально на устройстве, без аккаунта и облака | Must |

## Контекст / проблема

В приложении уже есть вкладки **Задачи | Заметки | Покупки** (`MainScreen` / `AppTab`), задачи с датами и повторами (`TaskEntity`, `RecurrenceType`), события/ДР. Медицинский контекст (анализы, курсы лекарств, «повторить через …») сейчас либо теряется в заметках, либо смешивается с обычными задачами без структуры «человек → анализы / назначения».

**Ценность:** локальный «домашний» контур здоровья рядом с задачами, с мостом в существующий планировщик через создание задачи на приём.

## Acceptance criteria

### Навигация

1. Given приложение, When открыт bottom bar, Then есть вкладка **«Здоровье»** между **«Заметки»** и **«Покупки»** (порядок: Задачи → Заметки → Здоровье → Покупки).
2. Given вкладка «Здоровье», When пользователь её открывает, Then показывается экран здоровья (не задачи / не заметки / не покупки).
3. Given вкладка «Здоровье», When нет ни одного человека, Then empty-state с CTA «Добавить человека».

### Люди

4. Given empty / список людей, When пользователь добавляет человека (имя обязательно), Then человек появляется в списке/переключателе.
5. Given уже **3** человека, When пользователь пытается добавить ещё одного, Then добавление недоступно (кнопка disabled и/или сообщение «Можно добавить не больше 3 человек»).
6. Given несколько человек, When пользователь выбирает человека, Then списки анализов и назначений относятся только к выбранному.
7. Given человек с данными, When пользователь удаляет человека, Then система требует подтверждения; при подтверждении удаляются связанные анализы и назначения этого человека (созданные задачи **не** удаляются автоматически — см. бизнес-правила).
8. Given человек, When пользователь редактирует имя (и опциональные поля из scope), Then изменения сохраняются.

### Анализы

9. Given выбранный человек, When пользователь добавляет анализ (название обязательно), Then пункт появляется в списке анализов этого человека.
10. Given анализ, When пользователь указывает плановую дату и/или отмечает статус (например «запланирован» / «сдан»), Then это отображается в списке.
11. Given анализ, When пользователь редактирует или удаляет его, Then список обновляется без влияния на других людей.

### Назначения (лекарства и визиты)

12. Given выбранный человек, When пользователь добавляет назначение, Then обязан указать **тип**: «Лекарство» или «Визит», и название; пункт появляется в списке назначений с различимым типом.
13. Given назначение типа «Лекарство», When пользователь указывает дозировку/комментарий и/или даты курса (если заданы в scope), Then поля сохраняются.
14. Given назначение типа «Визит», When пользователь указывает дату/время визита и/или комментарий (врач, клиника — в комментарии или отдельных опц. полях), Then поля сохраняются.
15. Given назначение, When пользователь архивирует или удаляет его, Then оно исчезает из активного списка (архив — Should).

### Создание задачи из назначения

16. Given назначение (лекарство или визит), When пользователь выбирает «Создать задачу», Then открывается поток с предзаполненным названием и выбранным сроком или повтором.
17. Given поток создания, When пользователь задаёт «через N дней» (и опционально время) **или** тип повтора задачи (ежедневно / свои дни и т.д.) **или** конкретную дату (для визита — часто сама дата визита), Then после подтверждения создаётся обычная задача (`TaskKind.TASK`) в общем модуле задач.
18. Given созданная из назначения задача, When пользователь открывает вкладку «Задачи» (список или календарь), Then задача **видна** по тем же правилам, что и остальные задачи (фильтры, группировка по дате, календарь).
19. Given назначение, When задача уже создавалась, Then можно создать ещё одну без блокировки; опционально показать индикатор «есть связанная задача».

## Бизнес-правила

- Данные здоровья — **отдельный домен**, не смешиваются с покупками и заметками как сущности; связь с задачами — только через **создание задачи** (и опциональную ссылку на назначение).
- Максимум **3** человека на устройство / установку приложения.
- Один экран «Здоровье» всегда в контексте **одного выбранного человека** (по умолчанию — последний выбранный или единственный / первый).
- Анализ и назначение принадлежат **ровно одному** человеку.
- Назначение имеет тип: **`MEDICATION` (лекарство)** или **`VISIT` (визит)** — иных типов в v1 нет.
- Созданная задача — обычная задача списка дел: тот же `TaskKind.TASK`, видна в списке и календаре; отдельный kind «здоровье» не вводим.
- Приложение **не** ставит медицинские диагнозы, не интерпретирует результаты анализов и не даёт рекомендаций по лечению (только учёт и напоминания).
- Удаление человека **не** удаляет уже созданные задачи в модуле задач; задача остаётся обычной.
- Офлайн-first, без аккаунта (как остальной продукт).
- Русский UI.

## Вне scope (v1)

- Загрузка/хранение фото и PDF результатов анализов
- Интеграция с клиниками, ЕГИСЗ, страховыми, аптеками
- Напоминания push отдельно от модуля задач (в v1 опираемся на задачи; F-001 — общий эпик уведомлений)
- Дневник самочувствия / давление / вес / трекинг симптомов (Could)
- Шаринг профиля здоровья с врачом или семьёй по сети
- Голосовой ввод анализов/назначений
- Медицинские калькуляторы, справочник препаратов, проверка взаимодействий

## Зависимости

- Навигация: `MainScreen` / `AppTab` — новая вкладка
- Создание задач: существующий `TaskRepository` / редактор задач / повторы (`RecurrenceType`, `recurrenceInterval`)
- Напоминания в срок — зависят от F-001; до F-001 задача на приём видна в списке/календаре без гарантированного push
- Бэкап (F-003): при появлении экспорта — включить сущности здоровья в round-trip (отметить в F-003 при реализации)

## Открытые вопросы

1. Обязательные поля анализа: только название + дата, или ещё «лаборатория», «результат (текст)», «норма»?
2. Для визита: отдельное поле «дата визита» обязательно при создании, или дата задаётся только при создании задачи?
3. Нужен ли deep-link обратно: из задачи открыть карточку назначения?
4. Бейдж на вкладке «Здоровье» — в v1 или позже?

### Решено (2026-10-19)

| Вопрос | Решение |
|--------|---------|
| Лимит людей | **Максимум 3** |
| Состав назначений | **Лекарства и визиты** (два типа) |
| Задача из назначения | Создаётся в общем модуле задач и **видна в списке задач** (и календаре) |
